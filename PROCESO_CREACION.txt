SIMULADOR PYTHON DE KEYTOOL - PROCESO DE CREACION Y GUIA DE DEFENSA
===================================================================

Este documento recopila las decisiones de arquitectura, desarrollo y la preparación para la defensa individual de código (Sesión 5, 20% de la nota final).

1. Análisis del problema y del manual del curso
------------------------------------------------
Analizamos los dos documentos de la práctica (el enunciado y el manual de teoría de criptografía CETI M2). Identificamos que el proyecto requería:
- Interfaz CLI con argparse que simule los comandos oficiales de Java Keytool (--help, --genkeypair/--genkey, --certreq).
- Criptografía robusta: pares RSA de 2048 bits con exponente e=65537 y firma SHA-256.
- Persistencia cifrada del almacén con protección multicapa.
- Control estricto de excepciones sin mostrar trazas (tracebacks) ante errores de usuario.
- Implementación de ampliaciones sustanciales (30% de la nota / 3 puntos).

2. Arquitectura modular
-----------------------
Dividimos la solución en dos módulos independientes:
- `mykeytool.py`: Interfaz de usuario, análisis sintáctico de argumentos CLI, preguntas interactivas con `getpass` e `input`, y orquestación de operaciones.
- `keystore.py`: Núcleo criptográfico y persistencia. Cifrado simétrico del almacén, derivación con PBKDF2, manejo atómico de ficheros, generación RSA y formateo de certificados/CSR.

3. Decisiones Criptográficas y de Seguridad
-------------------------------------------
a) ¿Por qué PBKDF2-HMAC-SHA256 con 600.000 iteraciones?
   Una contraseña de usuario no es una clave criptográfica uniforme. Si usáramos un simple hash (SHA-256 directo), un atacante podría realizar ataques de diccionario a billones de hashes por segundo en GPU. PBKDF2 ralentiza intencionalmente el cómputo mediante una función de estiramiento de clave (Key Stretching), y la sal aleatoria de 16 bytes imposibilita el uso de tablas Rainbow precalculadas.

b) ¿Por qué Fernet (AES-128-CBC + HMAC-SHA256)?
   Fernet proporciona "Authenticated Encryption" (cifrado autenticado). No solo cifra los datos para confidencialidad, sino que añade un código HMAC que garantiza la integridad. Si alguien manipula un solo byte del archivo `.pystore`, el descifrado falla inmediatamente con `InvalidToken`.

c) Doble nivel de contraseñas (Store Password vs Alias Password):
   Igual que el Java Keytool oficial, existen dos niveles:
   - La contraseña del almacén protege todo el contenedor en disco.
   - Cada clave privada individual está cifrada bajo el estándar PKCS#8 con `BestAvailableEncryption` (AES-256-CBC) usando la contraseña de su propio alias. Incluso si un atacante obtuviera acceso al archivo descifrado en memoria, no podría usar la clave privada sin su contraseña individual.

d) Formato de Almacén Binario Ilegible (`PKS1`):
   Para evitar que el almacén sea legible como texto plano o JSON al abrirlo en editores como Notepad o VS Code, el archivo se guarda en formato binario puro compuesto por el identificador mágico `b"PKS1"`, la sal de 16 bytes y el payload de bytes cifrados. Al abrir el fichero, el sistema o editor lo reconoce como archivo binario con caracteres no imprimibles.

e) Escritura atómica (`os.replace`):
   Para evitar que una caída de tensión o error durante el guardado deje el almacén corrupto, se escribe primero en un archivo temporal (`tempfile.NamedTemporaryFile`) y se reemplaza el archivo original atómicamente.

4. Ampliaciones Implementadas (Criterio de Evaluación: 30% / 3.0 pts)
----------------------------------------------------------------------
Para asegurar la máxima nota en el apartado de ampliaciones, implementamos las herramientas esenciales de Java Keytool:
1. `--list`: Lista las entradas del almacén, mostrando alias, tipo de entrada (`PrivateKeyEntry`), nombre distinguido (DName) y la huella digital en formato SHA-256 (igual que `keytool -list -v`).
2. Certificados autofirmados X.509 v3: Conforme al manual de teoría, la generación de clave (`--genkeypair`) crea automáticamente un certificado autofirmado inicial con validez de 1 año (365 días) y firma SHA-256 con RSA.
3. `--exportcert` / `--export`: Exporta el certificado X.509 de un alias a un archivo `.crt` independiente en formato PEM, listo para ser instalado en Windows o navegadores web.
4. `--printcert`: Comando para inspeccionar y parsear cualquier archivo `.crt` o `.csr` externo sin requerir la contraseña del almacén, mostrando titular, emisor, número de serie, algoritmo y huellas SHA-256 y SHA-1.
5. `--delete`: Permite borrar un alias del almacén con confirmación explícita (s/n).
6. Compatibilidad completa de alias de comandos: Soporte tanto de `--genkey` como `--genkeypair`, y de `--store` como `--keystore`, además de paso opcional de parámetros por CLI (`--alias`, `--file`).

5. Guía de Preguntas Frecuentes para la Defensa Oral (Sesión 5)
---------------------------------------------------------------
P: ¿Qué diferencia hay entre un archivo CSR y un Certificado Digital?
R: La CSR (Certificate Signing Request) es la solicitud que genera el solicitante; contiene únicamente su clave pública, su Distinguished Name (identidad) y está firmada con su clave privada para demostrar posesión (Proof of Possession). NO contiene la clave privada. El Certificado Digital es el documento final emitido y firmado por una Autoridad de Certificación (CA) que vincula legalmente esa clave pública con la identidad verificada.

P: ¿Cuál es la diferencia entre codificación, ofuscación, hash y cifrado?
R: - Codificación (Base64, ASCII): Cambio de formato sin clave ni intención de ocultar (reversible).
   - Ofuscación (Defang URL, ROT13): Dificulta el análisis manual o por antivirus, no usa claves criptográficas.
   - Hash (SHA-256): Función matemática unidireccional e irreversible de longitud fija; garantiza integridad.
   - Cifrado (AES, RSA): Transformación matemática reversible con clave secreta; garantiza confidencialidad.

P: ¿En qué consiste el cifrado híbrido en el protocolo TLS/SSL?
R: Combina lo mejor de dos mundos: usa criptografía asimétrica (RSA/ECDSA) únicamente durante el handshake inicial para autenticar al servidor y negociar una clave de sesión simétrica; una vez acordada, todo el tráfico posterior se cifra con criptografía simétrica (AES-GCM) por su altísima velocidad y bajo coste computacional.

P: ¿Qué roles componen la arquitectura PKI?
R: - RA (Registration Authority): Verifica la identidad física o jurídica del solicitante (DNI, poderes notariales), pero no emite certificados.
   - CA (Certificate Authority): Emite y firma digitalmente los certificados de las identidades validadas por la RA.
   - VA (Validation Authority): Comprueba en tiempo real si un certificado sigue siendo válido o ha sido revocado (a través de CRL o respuestas OCSP).

P: ¿Qué ocurre si se introduce una contraseña incorrecta del KeyStore?
R: El algoritmo PBKDF2 deriva una clave a partir de la contraseña errónea; al intentar descifrar los datos con Fernet, la validación del HMAC falla arrojando un `InvalidToken`. Nuestro software captura esto y lanza `StorePasswordError`, informando amigablemente al usuario sin trazas de Python y devolviendo el código de salida 1.
